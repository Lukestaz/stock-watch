# Default-off friends runtime and scheduled market integration

This patch connects account-runtime.mjs to the existing verification/consent service, evaluator and dispatcher. It adds concrete Alpaca HTTPS bars and a scheduled-handler implementation. Unlike earlier factory-only notes, future deployment can now activate these routes through the explicit reviewed runtime flags below. No live flags, secrets, cron, migrations or deployments are changed by this branch commit. Existing account/site routing remains unchanged with friends flags absent/off. The PR remains draft.

The Worker lazily loads friends code only when ACCOUNTS_ENABLED and FRIENDS_ALERTS_ENABLED are exactly true strings. It checks trusted origin, account/session dependencies, Gmail configuration and private schema metadata before using the service. Cloudflare socket imports occur only inside enabled initialization after schema checks. Missing setup fails closed without SMTP calls. Gmail and Alpaca credentials must be provisioned securely as Worker bindings; Actions secrets do not transfer automatically. No real secrets were accessed during development.

Routes are /api/v1/alert-destination/email, its /verify endpoint, and /api/v1/alert-consent/email. Existing services retain their session/origin/account-precondition guards. Same-origin GETs may have Origin normalized only with exact configured origin and Sec-Fetch-Site=same-origin. Edge admission uses Cloudflare-provided client metadata and the existing ACCOUNT_LIMIT binding before durable private request limits. No health output includes secrets, recipients or user rows. With the feature flag on, health appends readiness/enrolment/schedule-configuration booleans. These are configuration indicators, not proof of delivery or a registered/running cron. Initialization is cached per environment and fails closed until a reviewed redeploy after missing setup is corrected.

FRIENDS_SCHEDULE_ENABLED additionally requires configured Alpaca bindings for market work. FRIENDS_ENROLLMENT_ENABLED additionally requires that scheduled configuration. Both default off. No cron trigger is installed here: register and prove the schedule before enabling enrolment. The scheduled handler fetches each eligible shared symbol once, evaluates bars chronologically through the real account producer, drains up to ten queue items and calls retention cleanup. Only aggregate status/counts are logged. More than twenty active symbols returns capacity without partially monitoring users; capacity/admission policy must be reviewed before inviting users.

The Alpaca adapter fixes the host, delayed SIP feed, raw one-minute timeframe and a 15-60-minute observation window. Requests timeout after 15 seconds; JSON is capped at 256 KiB/1000 bars, unexpected pagination fails closed, and invalid/future/too-fresh bars are filtered. It never backfills before a user's monitor baseline. Provider failures create no new events for that fetch, while previously eligible pending events may still dispatch. Existing evaluation rechecks/rearming and dispatcher consent/lease/uncertain-outcome protections remain authoritative. Market API usage is bounded per job but does not share a provider-wide rate counter with existing caches/legacy jobs. Review provider entitlements, quotas and data precision before live use.
