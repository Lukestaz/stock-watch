# Session-bound email destination candidate: disabled

createSessionAlertDestinationApi connects the existing createIdentityService session authenticator, candidate destination routes and D1 verification adapter. It defaults disabled and is not imported by account-runtime.mjs or production composition. This patch changes no existing routes, enrolment guards, migrations or deployment workflows. Earlier API/store notes about missing session composition are superseded for this candidate only, not for production.

Enabling the candidate in trusted tests requires explicit HTTPS origin, D1-shaped database, Google client configuration/key-loader dependency, pre-auth admission function, account limiter, mail adapter and optional clock/provider configuration. Construction queries no database and sends no mail. Existing sessions are checked using their cookie-token hash, absolute expiry and idle expiry. Account IDs come from authentication, never request headers or JSON. Verification is account-bound and leaves enabled=0.

Admission must return literal true before session database access. The account limiter must return literal true before destination storage/mail. These are required hooks, not implementations of durable quotas or abuse protection. Runtime wiring must supply safe limits, shared credential-backed mail, and global/destination sending budgets before any production enablement. The factory receives a trusted key-loader dependency to satisfy the existing identity service; session-only verification does not initiate Google login or fetch keys.

The module handles only internal /v1/alert-destination/email and /verify paths. A future reviewed app integration must explicitly dispatch /api-prefixed requests; no new public route is exposed here. Real-mail verification, frontend controls, channel/target opt-ins, account alert evaluation and dispatch remain unfinished. WhatsApp remains unavailable for account delivery.

Run node --test worker/test/account-alert-destination-integration.test.mjs. Ten integration tests use real session authentication, route validation and durable SQL through temporary SQLite databases with the migration chain. Session rows/cookie headers are seeded by tests, not obtained from real Google login or browser cookie delivery. Mail and admission/limiter decisions are mocked. Coverage includes cross-account token rejection, invalid/expired/idle/revoked sessions, request-boundary checks, generic mail failure, expiry and concurrent one-time verification. No live D1, browser, real email or production-security audit is claimed.
