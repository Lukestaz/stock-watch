# Verification preview and assembled-service checks: not activated

The new site/account-alert-settings.mjs exports a verification client and explicitly mounted preview panel. No existing HTML, sign-in script or runtime imports/mounts it. Default disabled mounting does nothing. Adding this unused static module on the feature branch does not deploy it; a future main-branch merge may trigger the normal asset deployment workflow, but still would not mount it. No public verification routes are wired by this patch.

The client first reads the authenticated watchlist response's X-Watchlist-Account header, then sends it as an account precondition on verification requests. The server compares it to the actual authenticated session and returns 409 on mismatch before account limiting/storage/mail. This header is a precondition only, never authentication. Lower-level callers without the header retain existing behaviour. The guard protects the preflight-to-POST account-switch window, not every possible browser/session race.

The preview subscribes to the existing session-state interface, aborts pending client requests and clears address/code fields on session changes, discards stale responses and does not persist either value in local storage or URLs. Aborting the client does not undo server work already accepted. It uses textContent/DOM nodes, not user-supplied HTML. Buttons require explicit user actions; there is no automatic code request. Verification success explicitly reports alerts remain off. Email-price-alert and WhatsApp controls are disabled explanations, not working opt-in controls. Actual consent APIs/storage and account dispatch remain unfinished.
