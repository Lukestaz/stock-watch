# Verification-mail adapter and budgets: disabled candidate only

The mailer defaults disabled. No production composition imports it and no provider-specific transport is implemented here. No credentials are read, routes exposed or migrations applied. Migration 0007 is an unapplied proposal. Candidate routes now pass authenticated userId to the trusted mail callback; clients still cannot supply identity or provider fields. This extends the older sendVerification contract in ALERT_DESTINATION_API.md to {userId,to,token,expiresAt}.

createVerificationMailer requires a fixed configured sender, a trusted send(message) function, an atomic reserve function and explicit enabled=true. It sends one recipient a fixed verification-code template; caller-supplied sender, subject and body are ignored. Tokens are validated, expire within ten minutes and appear only in the trusted transport's message body, not links or reservation records. A provider adapter must enforce transport timeouts and return {outcome:'accepted'} only on explicit provider acceptance. No automatic retries or cross-channel fallback occur. Provider acceptance is not confirmed delivery.

createD1VerificationMailBudget reserves a slot in one conditional INSERT, including the existing account check and all quota predicates. Defaults are app policy, not provider limits: 50 global verification attempts per fixed UTC day, 5 per fixed UTC minute, 3 per account per UTC day, 3 per lowercased destination hash per UTC day, with a 60-second account-or-destination cooldown. Trusted configuration can change these. Reservations are charged before transport invocation and never refunded on failure or uncertainty. Concurrent reservations cannot both take the final database slot. A clock earlier than an existing reservation fails closed.

These budgets cover only this verification-mail path, not legacy stock alerts or other sending through the same Gmail account. A provider-wide aggregate quota and concrete credential-backed transport still require integration. Separate pre-auth admission and authenticated request limits are still required; these mail-attempt caps do not protect all route/database traffic. Destination hashing lowercases the whole address for conservative quota grouping but does not canonicalize provider-specific aliases.

Reservations store private account IDs and SHA-256 destination hashes, not email addresses or tokens. Hashes are pseudonymous, not anonymized; never publish them. There is deliberately no cascading user foreign key so account deletion cannot refund shared quotas. A reviewed retention cleanup must remove records only after every applicable window/cooldown has elapsed (retain at least 48 hours with default policy), with account-deletion/privacy handling reviewed before production enablement. Cleanup is not implemented in this patch.

Fourteen local tests use real reservation SQL, temporary SQLite, a targeted users/watchlists fixture and mocked transport. The committed tests use the existing bridge, which applies the repository migration chain in CI. Full-chain CI and actual D1/provider behaviour remain unverified until run. Coverage includes quota boundaries, isolation, concurrent reservations, non-refunded failures, invalid mail input and trusted route identity. One route test mocks verification storage; it is not a fully composed session/verification/mail production test.

Run node --test worker/test/account-verification-mail.test.mjs. No live mail is sent. Next steps are candidate composition with all real local adapters and mocked provider I/O, provider transport selection, retention/admission policies, explicit channel/target opt-ins and a separately approved production migration/deployment.
