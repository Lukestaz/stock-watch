# Durable email verification adapter: not production-wired

Migration 0006 and createD1AlertDestinationStore implement the durable contract described in ALERT_DESTINATION_API.md. Its older 'not implemented here' wording describes the route-only patch; this adapter now exists on this branch. Neither store nor candidate routes are imported by production composition. Migrations 0005/0006 remain unapplied to live D1.

Registration uses a D1 batch to upsert the current account's email destination, clear verification/consent, remove the old challenge and insert one hashed challenge with destination revision/address/provider/binding snapshots. Existing server-selected provider bindings are preserved. Same-address reissue replaces the hash. A nonexistent account returns false without creating a destination. Store arguments are trusted server-internal inputs; route-level mailbox validation is deliberately stricter than the adapter's defensive validation.

Completion uses one conditional UPDATE with RETURNING, requiring the account, hash, unconsumed state, creation/expiry interval and all destination snapshots. The consume trigger verifies that same destination and leaves enabled=0. Consumption and verification succeed together or roll back. Concurrent database consumers have one winner; accepted verification cannot be replayed. Changing the destination/binding invalidates the snapshot. Deleting a destination cascades its challenge so recreation cannot revive it.

Only hashes are stored. No SMTP credentials, raw tokens or sender implementation are added. Constructor emailProvider is trusted configuration for new destinations, not client input. Authentication must derive userId from a verified session before calling the adapter. These SQL account predicates do not substitute for session authorization. Do not log raw database errors: candidate routes already return generic storage failures.

One challenge row per account bounds current challenge storage; reissue replaces expired/consumed rows. A scheduled retention cleanup is not implemented. Issuance abuse limits, authenticated session composition, rate budgets, verification-mail adapter, opt-in controls and frontend still need implementation/integration before enablement. The verification timestamp does not enable stock alerts. WhatsApp is unchanged and unavailable for account delivery.

Run node --test worker/test/account-alert-destination-store.test.mjs. Twelve tests use the existing file-backed SQLite D1 bridge, the full migration chain and separate Python database connections for concurrency. They cover isolation, expiry, replay, destination/binding changes, overlapping operations and injected-error rollbacks. This is local SQL/adapter verification, not actual Cloudflare D1, real-session or live-mail verification. Production migration and deployment require separate approval.
