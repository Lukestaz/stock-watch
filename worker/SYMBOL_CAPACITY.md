# Email-symbol capacity admission: server guard

The initial policy is at most 20 distinct symbols with email_enabled=1 across all accounts. Multiple accounts selecting the same symbol share one reservation. Paused, unverified or provider-unavailable destinations retain their selected-symbol reservations. This conservative accounting prevents destination verification/resume from silently creating additional scheduler demand. A reservation is freed when the last account turns that symbol off, deletes the target or deletes the account. Merely pausing or changing an address does not free capacity. Counts are global; no other account symbols, identities or destinations are exposed to the browser.

The check is part of the existing conditional watchlist revision claim inside the consent batch, not a separate count-then-save operation. Failed admission returns null and leaves that request without the ownership marker used by later mutations. Opt-out bypasses the capacity predicate. The paused multi-stock resume guard and all revision/verification checks remain. Distinct new-symbol requests race for the final slot transactionally; same-symbol subscriptions share it. Rollback also rolls back the selected-symbol change. No schema migration is introduced.

This patch uses a fixed 20-symbol server admission limit to match the current production scheduler default of 20. Do not lower the schedule limit or raise the admission limit independently. Existing schedule capacity checks remain a safety backstop; already over-capacity data requires inspection and explicit opt-outs, not silently dropping monitored users. The guard does not repair existing data or change production flags. Direct database edits and any future alternate enrolment API must uphold the same invariant.

Nine added tests call the real store using the full migration-chain SQLite D1 bridge. They cover boundary rejection and unchanged state, sharing, paused reservations, last-subscriber release, concurrent distinct/same-symbol admission, rollback and opt-out above capacity. These new tests have not been executed in this patch-preparation turn; account CI must pass. Actual Cloudflare D1/runtime validation remains separate.

API and UI still map failed consent to the existing generic conflict response. A dedicated capacity response and user-facing explanation are follow-up work before launch. This patch is server-side admission only, not the complete capacity user experience or production activation.
