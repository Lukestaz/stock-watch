# Account email consent and event producer: disabled candidate

Migration 0009, createD1AccountAlertStore and createAccountAlertConsentApi add private consent/evaluation logic only. No existing runtime, consent UI, market fetcher or schedule imports them. No migrations are applied, no account is enrolled and no transport is called by this patch. Store enrolment and evaluation default off; the HTTP factory also has explicit runtime/enrolment gates. Production watchlist enrolment blocks remain unchanged.

## Private email consent

Candidate GET/PUT /v1/alert-consent/email uses trusted injected session authentication plus admission/account limiters, exact origin and bounded JSON. It is not yet composed into the real-session runtime. PUT requires the actual authenticated account precondition and exactly symbol, enabled, expectedWatchlistRevision, expectedTargetRevision and expectedDestinationRevision. Identity, verification and provider fields cannot be supplied by clients. Read responses expose that user's flags/revisions and verification status, not addresses or keys.

Opt-in requires the current target and verified destination revision. A single D1 batch conditionally increments the watchlist revision using an internal ownership marker, updates the email flag, maintains the global email destination gate, advances a consent revision, sets an observation baseline and cancels prior pending email deliveries for that symbol. Existing WhatsApp flags are preserved but never enabled by this interface. Opting out of one symbol leaves other subscribed symbols working. Opt-out can succeed after destination verification is lost. Stale preconditions return a conflict without partial mutation. Repeated successful consent writes deliberately create a new revision/baseline; retries with an old revision fail rather than silently reenrol.

The existing full-watchlist save rejects edits while any alerts are active. That guard remains: a future UI must offer explicit opt-out before target editing and must explain conflicts. Actual consent controls and session composition remain unfinished; the verification preview's alert buttons stay disabled.

## Observation-to-private-queue evaluation

The caller supplies trusted USD low/close observations and integer Unix observation/current times in chronological order. There is no market API call or public evaluation endpoint. One symbol observation evaluates all currently eligible accounts' distinct targets, without publishing destinations. Observations must be 15-60 minutes old, newer than consent activation and the last processed observation, finite/positive, bounded and have low <= close. Opt-in waits for a later observed market bar plus its data delay; no pre-enrolment historical alerts are generated. This time policy matches the delayed-data candidate, not live/executable prices.

Current watchlist/target and destination verification/flags/revisions are checked within the transactional evaluation. A per-batch ownership token claims eligible monitors; event/delivery inserts and arming changes commit together. Target means low <= target, near means target < low <= 1.05*target. Close >1.02*target rearms target; close >1.07*target rearms near. A target event disarms both. These comparisons use SQLite REAL USD values; precision/provider normalization still need production review.

Delivery keys capture user, symbol, target revision, kind, observed time, email channel, destination revision and consent revision. Duplicate/concurrent observations do not create another armed event. Cancelled or accepted rows are not reactivated by INSERT OR IGNORE. Pending email invalidation marks expired observations (older than two hours), changed revisions, opt-outs or unverified/changed destinations as ineligible. Claimed/accepted/outcome_unknown rows are deliberately not retried or rewritten by this producer.

## Not yet a dispatcher

No delivery claim lease, pre-send recheck, account price-alert formatter, sending quota reservation, outcome recording or SMTP invocation is implemented here. A future dispatcher must atomically claim, recheck all live consent/target/destination conditions immediately before provider invocation, handle concurrent opt-out and uncertain outcomes, and use only the recipient bound to that account. Do not treat pending queue rows as permission to send. Verification-mail SMTP currently accepts only the verification subject; it is not yet a price-alert sender. No exactly-once guarantee is made. Account event retention and provider-wide aggregate budgets remain future work.

Twenty-one tests passed locally using real new SQL against targeted SQLite fixtures and mocked HTTP authentication/admission decisions. The committed bridge applies the repository migration chain in CI. Coverage includes account/target isolation, consent conflicts, opt-out, revision invalidation, freshness, rearming, duplicate/concurrent evaluation and transactional rollback. This is not actual D1, real-session consent integration, browser consent or end-to-end delivery verification. New full-chain CI must pass before review/merge; all private migrations and production activation require separate approval.
